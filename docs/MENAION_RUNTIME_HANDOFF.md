# Menaion runtime handoff: inspection-only revision

## Implemented and verified offline

`scripts/inspect-menaion-runtime-handoff.py --inspect` inspects the existing Beget
Docker runtime and reads configuration/catalog facts only. The script is intended
to run through the repository's protected, main-only GitHub Actions SSH transport.
It has not been run on production as part of preparing this artifact.

It does not accept or read a password. It does not read stdin. It does not inspect
Kong, use an existing API credential, mint a token, issue an HTTP request, change a
role, write an environment file, or create/stop/remove/rename a container. Its
only SQL transaction is `BEGIN READ ONLY` followed by catalog SELECT and ROLLBACK.
An activation argument fails before any subprocess or input read.

Output is a fixed JSON schema of booleans, fixed status strings, known structural
field names, and counts. Raw Docker inspection, connection strings, environments,
passwords, hashes, SQL errors, exception details, and content rows are never
printed. The existing environment is parsed in memory to test equality and URI
shape. Role passwords are inspected only as `rolpassword IS NULL` inside SQL.
The environment directory must be user-owned mode 0700 and the environment file
must be a user-owned mode-0600 regular file with one hard link and no symlink.

The script reports:

- Immutable image resolution and image-default command/user/entrypoint/etc. match.
- Known HostConfig deviations, missing critical fields, and unknown field count.
- One expected network and actual URI-host membership in `supabase-db` aliases.
- Existing environment-file equality, audience presence, schemas, and pre-config.
- Exact migration version `20261002184929` and checksum
  `15265e48dcbf87b24b7aed34c296c2a4a83cbba132a5e33bffc0cfdd9469444c`.
- NOLOGIN/NOINHERIT/nonprivileged/password-NULL role state, no active dedicated-role
  sessions, exact dedicated memberships, and unchanged shared membership boundary.
- Database/role PostgREST configuration override presence.
- Effective inspector-session logging/audit observations without secret values.
- Five fixed known preload-module flags and an unknown-module count. Arbitrary
  library names are never returned; the inventory does not certify hook safety.
- Every Docker command is pinned to unix:///var/run/docker.sock; a saved remote
  currentContext cannot redirect the inspection.

A completed inspection is not an activation approval or proof that credentials
can be safely changed. `activation_ready`, `activation_implemented`,
`credential_logging_safety_proven`, and `exact_runtime_replacement_proven` always
remain false. An individual logging boolean is an observation, not a promise
about a different future session, all loaded hooks, or host-level auditing.

## Remaining evidence before an activation implementation

1. Run this read-only inspection in the reviewed production workflow and inspect
   the sanitized report. Do not provide `MENAION_REST_AUTH_PASSWORD` to this
   workflow revision.
2. Resolve any image/default, host-setting, environment, alias, role, checksum,
   or override mismatch. Do not rerun the original provisioner as a repair: it
   copies the shared authenticator and can destroy a later dedicated runtime.
3. Review the live database version, preload/audit modules and logging paths.
   In particular, error-statement logging, statement/duration/sampling logging,
   pgAudit, auto_explain, pg_stat_statements utility tracking and unknown preload
   modules must not leak credential SQL. Session observations cannot establish
   host audit safety. No logging or security setting is changed by inspection.
4. Prove how to reproduce all actual runtime settings using the existing
   immutable image and network, while preserving every unrelated environment
   and JWT setting. Retain the exact old container and privately back up the old
   env file before attempting a future swap.
5. Build and test compensating rollback for failure before, during, and after
   container renaming and role change. The rollback must verify the old runtime
   is serving and the dedicated role is restored to NOLOGIN/PASSWORD NULL.
   Process termination/host failure needs an explicit recovery path; a Python
   exception handler alone is insufficient rollback coverage.

## Future user-owned credential workflow (not implemented here)

Only after the reviewed activation/rollback artifact exists, the operator can be
instructed to enter their chosen dedicated password in the repository's GitHub
`production` Environment secret named `MENAION_REST_AUTH_PASSWORD`. The password
must never be requested in chat, generated by the assistant, passed as workflow
inputs/argv, or echoed. A future manual-only activation job must read the existing
GitHub secret and send it over pinned-host SSH stdin to a stored remote script,
with shell tracing disabled and no temporary runner secret file. The script's
source and password cannot share the same stdin stream.

The operator, rather than the assistant, must dispatch the credential-binding
job. A `production` Environment label does not imply a required reviewer: use the
actual configured protection rules, and do not claim approval from an absent
reviewer gate. The workflow needs a non-secret explicit action choice and exact
current-main verification, plus concurrency shared with other Menaion runtime
operations. The complete action and credential operation need their applicable
user authorization independently of preflight results.

Any future activation should alter only the already-created dedicated role's
LOGIN/password and the runtime URI user/password plus add `menaion_feedback` to
exposed schemas. It must preserve current JWT handling, leave the shared
`authenticator` untouched, and never expose `menaion_feedback_private`. Creating
feedback JWTs or installing an application token is a separate operation and is
not included in this handoff.

## Offline validation

Run:

    python3 -m unittest discover -s tests -v
    python3 -m py_compile scripts/inspect-menaion-runtime-handoff.py

Twenty tests passed during preparation. Coverage includes invalid JSON,
wrong-type booleans, duplicate/malformed environment variables, symlink/hardlink
and permission rejection, safe URI-alias matching, env/image/network/host drift,
secret-free failures, no stdin use or activation path, and reports that cannot
claim activation readiness.
